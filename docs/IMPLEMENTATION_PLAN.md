# תוכנית מימוש וסטטוס — WILD

עדכון: 12 בנובמבר 2026. המסמך מסכם מה מומש באפליקציה, מה פועל בפריסה הנוכחית, ומה עדיין נדרש או נדחה.

## תמונת מצב

היישום המרכזי פועל כאתר פרטי על VPS יחיד של Hostinger: Frontend ב־React/TypeScript, ‏Backend ב־FastAPI/Uvicorn, מסד SQLite ואחסון קבצים מקומי. זיהוי חיות ועריכת קליפים פועלים על CPU. הגישה מוגנת ב־HTTPS וב־Basic Auth משותף; אין כרגע חשבונות משתמש אישיים או הפרדת נתונים.

| תחום | סטטוס |
|---|---|
| העלאת מדיה, ספרייה ותצוגה מקדימה | הושלם ונבדק |
| זיהוי חיות עם SpeciesNet | הושלם ונבדק |
| עריכת קליפים ורינדור עם FFmpeg | הושלם ונבדק, כולל כתוביות בעברית |
| MusicGen ופס קול אוטומטי | מומש בקוד; נדרשת פריסה |
| ניהול תוצרים | פעולות בסיסיות קיימות |
| Google Drive | הממשק והייבוא מומשו; Drive כבוי בשרת הניסוי |
| פריסה פרטית בענן | הושלמה על VPS יחיד |
| גיבוי, שחזור, עומס והתאוששות | עדיין דורשים בדיקה והגדרה |

## שלב 0 — סביבת פיתוח ותשתית בסיסית

**סטטוס: הושלם.**

- Backend ב־Python עם FastAPI ו־Frontend ב־React, TypeScript ו־Vite.
- סביבת Python ו־Frontend עם תלויות, lint ובדיקות.
- FFmpeg ו־SpeciesNet מותקנים בסביבת השרת.
- בשרת הוגדרו נתוני היישום ב־`/var/lib/wild` והגדרות נפרדות בקובץ `.env`.
- Redis אינו בשימוש: תורי הזיהוי והרינדור פועלים בתהליך ה־Backend.

## שלב 1 — העלאה, ספריית מדיה ותצוגה מקדימה

**סטטוס: הושלם ונבדק.**

- יצירה וניהול של פרויקטים ופריטי מדיה.
- העלאת תמונות וסרטונים בחלקים; פס התקדמות ומונה שמציג כמה קבצים עלו מתוך הקבוצה שנבחרה.
- מגבלת העלאה של 50 MB לקובץ נבדקה: קובץ בגבול מתקבל וקובץ שחורג נדחה.
- יצירת תמונות ממוזערות, הצגת תמונות וסרטונים, ומסירת קובצי מדיה עם תמיכה ב־Range.
- קובצי AVI מסוימים עוברים remux אוטומטי עם `mkvmerge`, אם FFmpeg אינו מצליח לקרוא את המקור.

## שלב 2 — זיהוי חיות

**סטטוס: הושלם ונבדק.**

- SpeciesNet מנתח תמונות ודוגם פריימים מסרטונים על CPU.
- תוצאות הזיהוי נשמרות ב־SQLite וכוללות מין, ביטחון, זמנים ותיבות זיהוי.
- הממשק מציג זיהויים ומאפשר קפיצה לזמן בסרטון, סינון ותיקון ידני.
- סטטוס והתקדמות זיהוי מוצגים בממשק; זיהוי תמונה וסרטון קצר נבדק גם לאחר הפעלה מחדש של השירות.
- תוקנה בשרת אי־התאימות של התקנת Torch/TorchVision: הותקנה גרסת CPU מתאימה, ובדיקת NMS עברה.

## שלב 3 — עריכת קליפים ורינדור

**סטטוס: הושלם ונבדק.**

- בחירת תמונות וסרטונים, גרירה וסידור בציר זמן, חיתוך והגדרת אורך.
- אפשרות לכלול קטעים שבהם זוהו חיות, כותרות פתיחה/סיום, שמות מינים ומעברים.
- רינדור ברקע ל־MP4 באמצעות FFmpeg, עם הצגת סטטוס והתקדמות.
- רינדור קליפ וכתוביות בעברית נבדק.
- פס קול שנוצר אוטומטית אינו כלול בשלב זה.

## שלב 4 — מוזיקה אוטומטית עם MusicGen

**סטטוס: מומש בקוד; נדרשת פריסה לשרת.**

- מוזיקה נוצרת לפי תיאור וסגנון באמצעות `facebook/musicgen-small` ו-Transformers על CPU.
- המשתמש יכול להפעיל מוזיקה, לבחור סגנון ועוצמה; FFmpeg מערבב אותה עם הקליפ ומוסיף Fade בקצוות.
- יצירת המוזיקה מתבצעת בתוך תור הרינדור ברקע. תור CPU משותף מונע חפיפה בין זיהוי לרינדור.
- בדיקת VPS: 29.9 שניות מוזיקה נוצרו ב-128.4 שניות; שיא הזיכרון היה כ-3.6 GiB. הורדת המשקולות הראשונה היא כ-2.36 GB, והמטמון נשמר תחת תיקיית הנתונים.
- משקולות MusicGen הן ברישיון CC BY-NC 4.0; השימוש בתכונה מוגבל לשימוש לא-מסחרי ובהתאם לתנאי הרישיון.

## שלב 5 — תוצרים ושמירת עריכה

**סטטוס: מומש חלקית.**

- ניהול תוצרי קליפים כולל צפייה, הורדה ומחיקה.
- נתוני הקליפים נשמרים ב־SQLite והקבצים נשמרים באחסון המקומי.
- טיוטת ציר הזמן נשמרת בדפדפן המקומי. סנכרון טיוטות בין מכשירים או משתמשים אינו קיים.
- הפרדה בין הפקות מקומיות לענניות אינה רלוונטית לפריסה הנוכחית, שבה יש שרת יחיד ואחסון מקומי.

## שלב 6 — ייבוא מ־Google Drive

**סטטוס: מומש בקוד; כבוי בפריסת הענן הנוכחית.**

- קיימים OAuth, דפדוף בתיקיות, בחירת קבצים ותיקיות, ייבוא ברקע, ביטול, טיפול בקבצים גדולים וניסיון חוזר.
- בשרת הוגדר `DRIVE_ENABLED=false`; לכן חיבור Drive אינו זמין באתר הנוכחי.
- הפעלה עתידית מחייבת הגדרת פרטי OAuth וכתובות callback בדומיין, ולאמת את החיבור דרך Basic Auth. אין לשמור סודות במסמך או במאגר.

## שלב 7 — איכות, ביצועים ויציבות

**סטטוס: חלקי.**

**כבר קיימים ונבדקו:**
- בדיקות Backend עם pytest ובדיקות lint עם Ruff.
- בנייה ובדיקת lint של ה־Frontend.
- בדיקות API לעלאה, זיהוי, תצוגת מדיה, ייבוא Drive ויצירת קליפים.
- כלי מדידת משאבים מקומי: [benchmark_resources.py](../backend/scripts/benchmark_resources.py).
- תשתית Playwright ל־Chromium וחמש בדיקות E2E של ממשק המשתמש; כולן עברו. קריאות ה־API מדומות כדי שהבדיקות יהיו מבודדות ויציבות.

**עדיין נדרש:**
- להריץ בדיקת E2E משולבת מול Backend זמני עם מסד ואחסון מבודדים, כדי לבדוק את החיבור האמיתי ואת יצירת קובץ MP4. אין להריץ אותה מול נתוני משתמשים או השרת הפעיל.
- למדוד זמני עיבוד ו־CPU/RAM ב־VPS, כולל חפיפה בין זיהוי, רינדור וצפייה.
- לבדוק התנהגות מכסת האחסון, ניקוי העלאות לפי TTL ושימוש בדיסק.
- לבדוק הפעלה מחדש בזמן עבודת זיהוי/רינדור ואת מצב המשימות לאחר מכן.
- למדוד דיוק SpeciesNet על מדגם מהשטח, במיוחד בתנאי לילה/IR.
- לבצע בדיקת נגישות ו־RTL שיטתית.

### תוכנית בדיקות E2E עם Playwright

בדיקות הממשק הנוכחיות משתמשות בתגובות API מדומות ובקובץ MP4 סינתטי. הן בודקות את זרימת המשתמש בדפדפן, אך אינן מריצות זיהוי SpeciesNet או רינדור FFmpeg אמיתיים.

- טעינת האפליקציה והפרויקט, וידוא שהממשק בעברית ובכיוון RTL.
- העלאת תמונה וסרטון, הצגתם בספרייה ובדיקה שמונה ההעלאות סופר רק קבצים שהועלו בהצלחה; לוודא שקובץ מעל 50 MB נדחה.
- בדיקת ממשק הזיהוי עם תוצאת API מדומה: הצגת זיהויים וניווט מהזיהוי לרגע המתאים במדיה. הרצת SpeciesNet עצמו ודיוקו נבדקים בנפרד.
- הוספת מדיה לציר הזמן, שינוי סדר/חיתוך, הגדרת כותרות וכתוביות בעברית, רענון הדף ובדיקה שטיוטת ציר הזמן נשמרה.
- בדיקת זרימת הפקת קליפ עם תגובת API מדומה: נגן MP4, ניגון קובץ הבדיקה, הורדה ומחיקה. רינדור אמיתי ייבדק בנפרד מול Backend זמני.
- בדיקת תצוגה ברוחב שולחני ובמובייל, כולל היעדר גלילה אופקית בלתי צפויה וניווט בסיסי באמצעות מקלדת.

הבדיקות משתמשות בפרויקט ובנתוני מדיה מדומים/ייעודיים, ולא בנתוני משתמשים.

## שלב 8 — פריסה ותחזוקת ענן

**סטטוס: פריסה פרטית הושלמה; הרחבה עתידית נדחתה.**

**פועל כעת:** Hostinger KVM 4 עם Ubuntu 24.04, ‏Caddy ו־HTTPS, ‏Basic Auth, שירות systemd יחיד, SQLite ואחסון מקומי. ה־Backend פועל ב־`127.0.0.1:8010`; הפרונט מוגש מ־`/var/www/wild`; נתוני היישום נמצאים ב־`/var/lib/wild`.

**עדיין נדרש לפריסה בטוחה לטווח ארוך:**
- להגדיר גיבוי חיצוני עקבי של SQLite והמדיה ולבדוק שחזור.
- לקבוע נוהל ניטור, התראות וניקוי אחסון.

**נדחה ואינו נדרש לניסוי הנוכחי:** Docker/Compose, ‏GPU של NVIDIA, מעבר ל־PostgreSQL או S3, מערכת תורים חיצונית, התחברות אישית למשתמשים ו־i18n. לפני פתיחה לציבור או שמירת נתונים פרטיים למשתמשים נדרשים אימות משתמשים, הרשאות והפרדת נתונים; Basic Auth משותף אינו מספק זאת.

## סדר עדיפויות להמשך

1. להגדיר גיבוי חיצוני ל־SQLite ולמדיה, ולתרגל שחזור.
2. לבדוק מכסת אחסון, ניקוי TTL וניטור מקום פנוי.
3. למדוד עומס ומשכי עיבוד בשרת, ולבדוק התאוששות אחרי עצירת שירות בזמן עבודה.
4. **הושלם:** בדיקות E2E של ממשק המשתמש עם Playwright לפי התרחישים שבשלב 7 (5 בדיקות עברו ב־Chromium; ה־API מדומה).
5. **בדיקת E2E משולבת מול Backend — השלבים הנדרשים:**
   - ליצור תיקיית בדיקה זמנית וייחודית, ולהגדיר בה את `STORAGE_DIR`; כך גם SQLite (`wild.db`) וגם קובצי המדיה יישארו מבודדים מנתוני הפיתוח והשרת.
   - להפעיל את ה־Backend על `127.0.0.1` ובפורט בדיקה פנוי, עם `PRELOAD_MODEL=false` ו־`DRIVE_ENABLED=false`. הבדיקה תתמקד בהפקת קליפ אמיתית עם FFmpeg, לא באיכות הזיהוי.
   - להפעיל את Vite עם `API_URL` שמצביע ל־Backend הזמני, ולהריץ תרחיש Playwright ללא `page.route` או הדמיית API.
   - דרך הממשק להעלות קובץ תמונה/וידאו סינתטי וקטן, לוודא שהוא מופיע בספרייה, להוסיף אותו לציר הזמן ולבקש הפקת קליפ.
   - להמתין עד שה־API מחזיר סטטוס `done`, ואז להוריד את התוצר ולוודא שהתגובה היא MP4 לא ריק; לאמת באמצעות `ffprobe` שהקובץ קריא ושהווידאו מקודד ב־H.264.
   - בסיום לעצור את השירותים ולמחוק רק את תיקיית הבדיקה הזמנית שנוצרה להרצה זו. אין להריץ את הבדיקה מול השרת הפעיל או נתוני משתמשים.
6. **בדיקות איכות:** למדוד דיוק SpeciesNet בתנאי לילה/IR ולבדוק נגישות ו־RTL.
7. לשקול MusicGen, Docker או תשתית מרובת משתמשים רק אם צורכי המוצר יצדיקו זאת.
